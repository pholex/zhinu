# SDK P4-R 可靠性验收矩阵

制定日期：2026-09-30；源码参考复核：2026-10-01。
适用对象：`xiaoyu-agent-sdk` 0.58.0 及后续候选版本。

本文将现有 SDK 契约转成可执行的可靠性验收方案。时长、负载和数值阈值是建议的
验收标准，尚未全部执行，不表示 SDK 已有相应生产保证。功能与边界契约见
[SDK 指南](sdk.md)，首版验证记录见 [验收记录](sdk-validation.md)。

完整矩阵尚未验收通过。本地候选批次已冻结
`tests/reliability/sdk-local.json` 的时长、轮数、阈值和随机种子；原始证据见文末。
未纳入该批次的矩阵负载仍是待执行标准，不表示 SDK 已有相应保证。

验收以 SDK 公开契约和测试断言为依据。恢复测试分别核对持久化记录、工具调用
和业务副作用；存储写入幂等不代表外部业务动作 exactly-once。

## 验收范围与环境

- 固定内核/SDK 版本、Git 提交和制品 SHA-256；源码与已发布制品分别标记。
- 平台：Linux、macOS、Windows；Python：3.11、3.14，共六组。
- 使用临时工作区、测试专用日志目录和可核对的业务副作用账本。
- 脚本模型提供确定性的调度、错误和修复结果；本机 HTTP 服务提供真实传输故障；
  真实 MCP 子进程覆盖进程与管道；真实模型单独记录供应商、模型和协议。
- `chat`、`responses`、`anthropic` 分别列覆盖情况；未测协议不得从其他协议推断通过。
- 进程强制终止只作用于测试创建的宿主/MCP 进程，绝不终止其他进程。

| R08 | 宿主回调故障 | 审批、工具、hook 抛异常、超时、异步取消、同步阻塞；每类 100 次 | 审批/hook 按契约拒绝；工具错误可供模型处理；同步阻塞不报告已关闭；解除阻塞后 close 成功；借用 client 不被 SDK 关闭 |
| R09 | 存储故障与锁竞争 | 两个进程竞争同一日志；注入写入/关闭的权限错误、ENOSPC、I/O 错误；每类 20 次 | 单写者有效；存储故障显式报告，不无声改为无日志模式；失败后的锁/资源状态可核对；恢复失败不覆盖原日志；故障解除后按契约重试或新建会话 |
| R10 | 结构化修复与预算 | 合法 null、非法 JSON、schema 不符、修复耗尽、迭代/token 预算停止、修复中断；每类 100 次 | 仅 valid 可消费 output；重试次数和 usage 正确；预算停止后无额外收尾请求；SDK 不重跑整个业务任务；账本记录模型重新请求同一动作的情况 |
| R11 | fork/rewind 与外部编辑 | 多轮后 fork；检查点后外部修改/删除文件；恢复操作失败；每类 20 次 | fork 历史与资源独立；冲突保留外部文件和对话；partial/conflict/unavailable/failed 等结果符合实际；重启不宣称恢复进程内文件快照 |
| R12 | 关闭竞态与所有权 | 执行中 close、重复 close、HTTP/MCP 清理阻塞、后台任务收尾；每类 100 次 | 正常关闭满足资源阈值；超时保持 closed=false，拒绝新任务；重试等待已有清理任务，不重复创建清理 worker；资源未结束时不提前释放日志锁 |
| R13 | 真实模型持续集成 | 每个拟声明支持的供应商/模型/协议组合，连续至少 1 小时、至少 100 个任务；覆盖多轮、审批工具、结构化修复、流式与中断 | 无 SDK 崩溃、死锁、会话混淆或假 valid；确定性业务任务最终有效率至少 99%；每次失败均归因；供应商不可用须补跑，不能算验收通过 |

R01/R02/R03 等短任务可循环到满足最低时长；不能以快速完成轮数代替持续运行。
R13 的任务应有确定答案和明确 schema，避免把开放问答质量当可靠性结果。
R06 的可恢复会话判定取决于实际执行阶段；必须记录恢复动作和下一轮结果。

## 时间与资源阈值

以下计时阈值只用于受控本机测试：无外部网络延迟，回调及测试服务按约定响应。
真实模型延迟单独记录 p50/p95/p99，不套用本机阈值。

- 合作式中断：注入后测试传输在 100 ms 内提供下一边界，本轮在 2 秒内结束。
- 未返回的同步回调/模型请求：不要求强制终止 Python 线程；阻塞时须正确超时并保留
  资源所有权。解除阻塞后，在受控环境中 5 秒内完成下一次正常关闭。
- `close_timeout` 是每个关闭阶段的等待上限，不是整个 close 的总耗时上限。
  记录各阶段耗时，禁止用单个全局时长断言错误判失败。
- 正常 close 返回后，测试创建的 worker、MCP 子进程及读线程、后台任务必须归零；
  允许采样器在 5 秒内确认。线程/句柄数回到预热后基线，最多允许 2 个能明确归因
  于测试框架或监控的常驻资源；SDK 自有资源残留不适用该容差。
- 预热 10 分钟后每 10 秒采样 RSS、Python 存活分配、线程、句柄/FD 和子进程数。
  使用固定历史大小或会话轮换的负载，测试 client 不保留全部请求，排除账本/采样器
  的线性积累。R01 的无限增长历史另列，不能用它判断资源泄漏。
- 受控固定负载下，最后 10 分钟 RSS 中位数相对预热后首个 10 分钟增长不超过
  `max(20 MiB, 基线的 10%)`；GC 后 Python 存活分配增长不超过 5 MiB；最后
  30 分钟 RSS 线性拟合斜率不超过 1 MiB/分钟。三项都满足才通过该资源门禁。
  超出阈值须保存分配快照并归因，不因 OS 分配器缓存直接宣称 SDK 泄漏。
- Windows 记录句柄数，Linux/macOS 记录 FD 数；不能用线程指标代替进程或句柄检查。

## 崩溃与副作用边界

宿主进程死亡自动释放 OS 日志锁，但不表示外部动作回滚，也不保证所有已返回结果
在突然断电后持久保存。本矩阵验证进程强杀，不验证断电、磁盘控制器缓存或 fsync
持久性保证。

R05 必须记录三个独立事实：动作账本是否提交、工具结果是否完整写入日志、恢复后
模型是否重新请求动作。SDK 不承诺 exactly-once；使用宿主幂等键的样例要求账本只
提交一次，不使用幂等键的样例要求准确记录重复风险，不应错误宣称 SDK 自动消重。

宿主强杀绕过正常 close。应单独记录 MCP 孤儿进程是否存在和测试如何收回；当前契约
不保证宿主崩溃自动清理所有第三方进程。若业务要求零孤儿进程，则另立要求，增加
宿主监督进程/进程组策略，不能用正常关闭测试证明该能力。

## 执行批次

1. 确定性批次：R01–R12 在六组平台/Python 上执行；每组独立保存报告。
2. 真实集成批次：R13 按供应商/模型/协议执行。执行前固定请求/token 或金额上限，
   到上限立即停止，未达到时长和任务数的批次记为未完成；不得把软 token 预算当硬
   费用上限。
3. 持续运行批次：主部署环境额外运行 24 小时固定负载，至少 10,000 个业务回合，
   混合多轮、会话轮换、MCP 与可恢复故障，应用上述资源门禁。72 小时作为扩展验证，
   不计入当前建议的必需门禁。

正式执行前，在固定环境至少采集三次健康基线，将延迟和资源分布用于标定；并发
测试同时采集串行对照，检查是否意外串行化。候选阈值须写明来源：业务 SLA、契约
不变量、健康基线倍率或经解释的绝对上限。内存增长需归因到存活对象或所有权，
不能只凭 RSS 判断。指标未采集记为 unavailable，不按零值通过。

阈值文件冻结后再执行验收批次，失败后修改阈值属于新方案，原失败记录必须保留。
24 小时运行属于当前候选配置，不因本文写入即成为产品的必需保证。

完整 P4-R 通过需冻结后的执行批次全部完成，包含 R14–R18 对应 P4 能力，所有
必需场景通过，且无未归因失败、无未关闭的契约违背问题。若只完成部分平台/协议，
报告必须明确限定验证范围。

## 报告与证据

### 证据与实验规则

证据按批次与试验组织。
测试断言/业务评分、证据完整性、对照可比性分别记录，三者不互相代替。

- 每次批次保存 manifest，包含任务集与 schema/评分器的哈希、阈值文件哈希、制品
  哈希、依赖清单、工作区起点、故障种子和配置。源码脏状态须捕获补丁及新增文件，
  仅记录 Git HEAD 不足以复现；起点不可验证则明确标记。
- 每次试验保存 `scenario_id`、`trial_id`、`run_id`、基线/候选身份、实际模型和
  协议、起止时间、退出状态、断言、指标、异常和产物位置。保留重复尝试，不能把
  重跑成功覆盖首次失败或将重试次数当独立样本。
- 历史日志作为参考证据。只有起点、任务、评分器、运行条件和样本身份可核对时，
  才能进入匹配对照；多项条件同时变化的结果只做描述性比较，不归因为某项 SDK
  改动。比较时记录哪些变量固定、哪些改变、哪些未知。
- 小羽按冻结的重复次数执行，单次冒烟只报告观察事实；率指标同时
  给出成功数/总数及置信区间，不能用很少样本宣称 99% 的生产保证。
- 缺失 usage、未获取的资源指标、工具结果未知和未完成试验须显式呈现。
  不能将缺失计为零成本、零泄漏或成功，也不能凭会话已连接/空闲判断本轮完成。
- 恢复证据分别记录“机制存在”“入口与后置条件连通”“已演练”，另列本次
  pass/fail；已演练可以失败。记录资源/动作身份、前状态、恢复决定、执行结果、
  后状态、残留副作用、负责方与具体阻碍。
- 汇总保留版本/场景/平台/协议的覆盖清单，每个结论链接原始试验，失败关联修复
  任务和复测证据。对照结论按场景给出，不生成掩盖失败项的单一总分。

每次执行至少记录：场景编号、开始/结束 UTC、提交/版本/制品哈希、OS/Python、
模型/协议、随机种子、配置、轮数/时长、注入阶段、断言结果、延迟分位数、资源曲线、
异常链的脱敏摘要、恢复前后日志摘要、动作账本和残留资源列表。

判定只能为 `passed`、`failed`、`blocked`、`not_run`。因供应商故障、费用上限或
测试环境限制未完成的批次不得写 passed；失败重跑保留首次失败证据。
报告和日志不得包含真实凭据；脱敏检查使用测试密钥和合成业务数据。

建议产物：每批 JSON 明细、资源 CSV、脱敏故障日志，以及汇总 Markdown。报告需
关联稳定的测试脚本/提交，避免仅凭终端输出认定验收。

### 保留的失败、修复与环境对照

- 30 秒、无预热预检的 RSS 斜率约 2.10 MiB/分钟，超过 1 MiB/分钟门禁；原报告
  保留为失败，未降低阈值。它不替代含十分钟预热的一小时批次。
- 三协议 HTTP 故障注入发现 Anthropic 缺少 `message_stop` 可能误判完成，已修复；
  Responses/Anthropic 的缓存计量及缺失 usage 同步修正。CLI JSON 兼容性、慢遥测
  关闭重试等失败与复测过程见验收记录。
- 常驻进程登记工作区曾重复解析全部历史路径，造成平方级开销。保留历史不信任
  规则的增量缓存修复后，同一带 CPU 分析器的 15 轮 R11 负载从 8.663 秒降至
  2.277 秒。此前长批次因此主动中断并重冻源码；已完成试验、首次失败与中断原因
  保留，不把被替换的批次写成通过。
- Windows x64 仿真并行批次出现 15 秒宿主进程守护超时。探针测得依赖导入
  18.234 秒、会话初始化/运行约 0.4 秒；串行及原生 ARM64 预热对照另存。
  未放宽守护阈值；架构、并发、预热均变化，不声称单一因果或普遍性能优势。
- Windows 首次快照缺少示例、跳过对象不可 JSON 序列化的问题已修正并保留原日志。
  macOS 3.11 一次补验的四个 CLI golden 失败源于父/子进程源码路径不一致，统一
  `PYTHONPATH` 后同组 281 项通过；安装 wheel 的隔离冒烟另行执行。

- Windows 原生 ARM64 与 x64 的 8 路 SQLite 生命周期均曾复现 `database is locked`。
  同一 adapter 增加有上限的 FIFO 写入排队后，原生 ARM64 与 x64 同负载复验分别在 171.205 / 242.278 秒通过；原始
  错误链、修复前后快照和诊断封装单独保存。Linux 后续发现的初始化窗口另由上文
  最终补验关闭。未改 `timeout` 或 `FULL` 同步强度，跨 adapter/进程仍依赖 SQLite 锁机制。
- Windows 3.11 最终存储批次的生命周期功能全部完成，但内存模式句柄增长超限。
  对照发现验收脚本保留已关闭的线程池对象：普通线程池增加 12 个句柄，释放引用
  即回到原基线。修正脚本后以 `handles-lifecycle` 独立批次复验，两表保留原失败
  与最新结果；SDK 运行时、负载和阈值未改。新增脚本回归验证资源采样前释放线程池。
  修正后两组 Windows 生命周期通过；尚未启动的旧快照生命周期由这些最终版本
  的同配置结果替代，原队列记录为未执行，避免重复已知采样偏差的旧实验。
- 一次全量回归误用仅安装 SDK 依赖的环境，缺少 rich/prompt_toolkit 等测试依赖；
  更正为项目完整测试环境后复跑，原日志保留，断言未改。
