# SDK / serve 迟到回答机制设计

状态：完整目标设计稿。2026-10-05 已实现 SDK 前三批与 serve 首批：持久化、可选前台等待、
幂等提交／取消、安全 step／下一轮接纳、恢复与版本观察。当前可调用 API 和首版限制见
[持久化待答](sdk-deferred-questions.md)与 [HTTP 问答](serve-questions.md)。
服务端自动唤醒和通用后端能力仍为拟议接口。目标是在用户回答偏好问题期间继续独立工作，同时确保回答经过
持久化、去重和接纳后才显示为已送达模型。

## 适用范围与兼容

当前源码的 SDK 已新增基础 `SessionOptions.asker` 回调桥接，可接同步函数，
AsyncSession 也可接异步函数；它仍等待回答且不接纳迟到结果，尚未发布。
见 [基础提问接口](sdk.md#宿主提问回调当前源码新增)。持久化服务首版与该回调互斥，
仅开启 QuestionOptions 时生效，尚未发布。

当前实现取舍：默认等待为 0，宿主显式设正数才进入 open；及时与迟到回答统一
先 queued，再使用安全 step／下一轮边界接纳。工具只返回状态回执，答案只进
普通用户历史，避免工具结果与回答状态之间新增事务窗口。SQLite 单条事务记录
同时保存接纳状态和历史消息，暂不用双存储补结算；观察流允许合并中间转换，
包括 question.opened。serve 另用严格 JSONL 单记录提交适配，共用状态机；后续再引入其他存储，不能把本文整体标为已完成。

当前 `Agent(asker=...)` 的同步契约保持原样：问题列表输入，答案字典返回。
现有 TUI 与没有问答前端的 headless 调用不改变行为。新机制由 SDK/serve 宿主
显式开启，配置独立的 `QuestionOptions`，不把协程直接传给现有 `asker`。

仅用于信息、偏好、约束的澄清。工具审批、权限升级与退出规划模式继续走审批
协议；超时、默认选项、连接中断、关闭面板都不能转换成批准。确实依赖回答的
工作必须保持等待；模型可继续的是与该回答无关的工作。

## SDK 与服务端接口

SDK 已增加独立问题服务：`Session.questions` / `AsyncSession.questions`。
两者提供 `list_pending()`、`answer(question_id, answers, idempotency_key)`
和 `cancel(question_id)`；异步版本的方法可 await。问题选项包含
`foreground_timeout_seconds`，默认 0 表示立即转入待答，显式正数（例如 60）
开启前台等待。超时只转为 pending，不表示选择默认值。

模型工具仍叫 `ask_user`，仅开启新服务的会话接入持久化等待，模型 schema 保持原样。问题批次由宿主
生成不可复用的 `question_id`，每题有稳定 `item_id`，不用自然语言题目作键。
及时回答时工具返回 queued 状态回执，答案在安全边界接纳；超时返回：

```json
{"status":"pending","question_id":"q_123","message":"尚未收到回答，可继续独立工作。"}
```

serve 已实现端点（创建会话需显式开启 questions）：

| 操作 | 端点 | 结果 |
|---|---|---|
| 查询待答 | `GET /session/{id}/questions` | open / pending / queued，含版本号 |
| 提交回答 | `POST /session/{id}/questions/{qid}/answers` | 持久化入队 202（接纳状态另行查询） |
| 关闭问题 | `DELETE /session/{id}/questions/{qid}` | 204；重复取消幂等，已接纳返回 409 |

回答体含 `answers: [{item_id, selected, custom, skipped}]` 和幂等键。
所有问题必须各出现一次；允许显式跳过，拒绝遗漏、重复 ID、未知选项和类型错误。
自由文本有大小上限，返回 400/413；未知问题 404，过期代或与已有答复冲突 409。
端点沿用会话访问控制，问题 ID 本身不授予跨会话访问权。不能把问题服务当作
提交任意用户消息或审批答复的旁路。

## 状态机与接纳点

```text
open ──超时／中断／恢复──> pending
  │                        │
  └──────答复持久化─────────┴──> queued ──进入用户历史──> answered
open / pending / queued ──显式取消或重置会话──> cancelled
```

超时只结束这次前台等待，不取消轮次，不生成空答案。收起 UI 不提交任何内容。
同一批问题的及时答复与超时争用同一把锁或存储事务；唯一胜者决定工具回执为
queued 还是 pending。所有回答都作为带来源与 question_id 的用户输入进入历史，
不能用 operator/system 通知提高其权威。

入队不等于模型已看到。`queued` 状态保留原问题，UI 显示“已提交，等待接纳”。
接纳发生在同步内核现有 step 边界：追加答案消息成功后才发 `question.answered`。
消息同时包含 `answer_id`，恢复时可查证已经接纳，避免重复注入。

不能直接复用 `Agent.steer()` 的内存队列作为可靠存储：现有实现会在新轮开始
清理陈旧插话，也不支持问题 ID、持久化和跨重启去重。实现时增加独立的待答服务，
只复用 step 边界调度点。内核仍同步，不为每个问题创建常驻工作线程。

## 持久化与崩溃恢复

SDK 的问题存储与会话存储共用 SQLite；serve 共用带写锁与同步确认的 JSONL 日志。最小记录包含会话 ID、会话代数、
question_id、tool_call_id、题目、状态、版本、answer_id、幂等键和答案载荷。
写入使用存储事务或 compare-and-swap；服务启动时必须验证后端支持这一能力，
不能静默退回无锁文件。问题状态和待投递答复在同一事务中落盘。

后续若引入无法合并状态与消息提交的其他后端，可采用可重放投递（当前两种适配器均不需要）：

1. 持久化 `queued` 与唯一 answer_id，再确认 HTTP 202。
2. 内核边界追加带 answer_id 的用户消息。
3. 问题表标记 answered，发布已接纳事件。

若在 2 与 3 之间崩溃，恢复先查会话日志中的 answer_id，再补结算，不重投。
若日志没有该消息，则继续投递。及时答复也先持久化 queued，工具结果仅含状态回执；完整答案沿用同一历史
接纳路径，不需要第二套“工具结果已写入”的补结算。

进程重启不恢复易过期的客户端倒计时。已持久化但仍 open 的问题转 pending，
旧轮次的悬空 tool_call 按现有历史修复规则收束；问题本身仍能回答。
reset / 删除会话增加代数并取消旧问题与待投递项；旧请求永远不能注入新会话。
fork 不继承可回答问题，恢复同一会话则保留其待答项。

## 幂等与调度

相同幂等键和相同答案重复提交返回原回执；相同键不同内容返回 409。
同一问题不同键再次答复也不能形成第二条投递。queued 的取消与接纳竞争时，
事务决定胜者；已接纳答案不可通过取消撤回。

运行中的会话在下个 step 边界接纳。空闲会话发布 `question.reply_queued`
通知，由宿主决定是否提交新一轮；serve 可配置自动唤醒，但一次会话只准一轮，
已有用户输入优先。唤醒需携带会话代数和任务版本；取消、重置后队列里的旧唤醒
必须撤销，不能堵住后续用户输入。等待期不消耗模型 token；唤醒后的轮次沿用
已有预算，预算耗尽则保留 queued 并显示原因。

## 事件与验收

SDK 已提供状态观察事件，serve 复用事件缓冲／SSE： `question.opened`、`question.pending`、`question.reply_queued`、
`question.answered`、`question.cancelled`，都含 session_id、question_id、
版本和来源工具调用 ID。UI 重连先取快照再按版本消费事件，丢弃旧版本。
已有消费方跳过未知 kind；上线时同步公开 API 清单及协议文档。

已实现部分与后续服务端实施需覆盖的确定性测试：

- 答复与超时同一时刻发生，只产生一份答案；断开 UI 不会批准或取消任务。
- 重复请求、不同幂等键及超时重试均不会重复投递。
- 入队前、入队后、日志落盘后但结算前崩溃，恢复后最多接纳一次。
- 取消排队与接纳竞争、重置后旧答复、fork、删除会话均不串入新轮。
- 多个客户端回答同一问题，只有一个成功；重连显示 queued 与 answered 的区别。
- 无前端、预算耗尽、存储写失败时给出明确状态，不遗失已确认接收的答案。
- 审批工具不能走本协议，默认选中项永远不等于提交。

建议作为独立功能分支实施：先完成存储与崩溃恢复契约，再接 SDK/serve（已实现首版），最后接
前端。无需在工具生成进度或只读会话诊断中提前引入这套持久化状态机。
