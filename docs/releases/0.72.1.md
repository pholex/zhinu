# 0.72.1（2026-10-15）

自 v0.71.1 以来的变化。

## 行为变化（升级前看一眼）

- 发版不再「推 main 等 CI 绿再打 tag」，改为 release.py 打完 tag 后 `git push --atomic origin main vX.Y.Z` 一次推走；CI 红了版本号就烧掉换一个。（56e0259）
- release_notes.py 默认不再调模型润色，要润色显式 --polish； --validation 默认 auto（读 nightly 记录），不附写 none。（56e0259）
- 发版说明的「行为变化」一节改从 commit 正文 footer 生成，写提交时要把 用户可感知的变化放进 `行为变化:` 段落。（56e0259）

## 新功能

- release：发版一条命令 + 一次 push，CI 不重跑，自测改 nightly，说明全自动（56e0259）
  对比业界同类工具的发版节奏后量了一下：xiaoyu 发版频率并不低（10 天 11 版），慢在
  每版 45–60 分钟有人盯的串行仪式——pre-push 全量、等 ci.yml 绿、再打 tag、release.yml
  把同一提交的 CI 再跑一遍、真模型自测、人工润色说明并手写「行为变化」、发后逐项核对。
  这次把仪式降到一条命令和一次 push，之后无人值守：

## 修复

- runtime：完善流末对账与失败诊断（e865f3a）
  内容拒绝经过流错误通道时不应反复重试，迟到的工具身份也必须与已有参数配对。
  压缩跳过与摘要失败需要分开留痕，编辑转义不确定时只提示重读，避免猜测替换意图。
  补充离线回归与拒绝场景快照，保持已有公开接口和审批语义。
- gitsafe：宿主侧 git 不抢 index 锁、解析用输出钉死形状（6a918c6）
  宿主自动起的 git（@ 补全的 ls-files、worktree 建查删、宸枢的 diff/merge）
  之前只防仓库配置注入，没管两件"当读者"的事：
- runtime：加固会话恢复、文件编辑与钩子执行边界（6391a58）
  长会话中的错误参数、外部文件修改和延迟取消可能造成错误副作用，
  而通知滞留与无界钩子输出会影响恢复后的可用性和内存稳定性。
  统一工具参数校验，以内容指纹和原子写入保护编辑，并在取消时保留
  真实执行结果、回收钩子进程、限制双路输出收集，使下一轮仍可继续。
- release：预检对未跟踪文件只提醒不拦（b573522）
  发版提交只 add 点名的文件，未跟踪的本机产物（实验结果目录之类）进不了
  提交，没必要为它们开 FAIL；已跟踪文件有改动才算脏。
- release：预检遇到还在跑的 CI 只提醒不拦（860bc29）
  新流程是打完 tag 一起推、由发版工作流的 gate 等 CI 结论，预检时刚推的
  main 几乎总在跑；把 in_progress/queued 当失败会逼人回到旧的串行等待。
- release：publish 只看 artifacts 的结论，不再被跳过的测试连带跳过（1d90f34）
  publish 没写 if，按默认要求链路上游全部 success；gate 核实过 CI 后把
  test / sdk-test 跳过，publish 就跟着 skipped——v0.72.0 的发版工作流全绿
  却什么都没发出去。改成与 artifacts 同样的写法，只认直接上游的结论。

## 其它

- experiments：增加提示词成本与推理回放测量入口（f18bfd9）
  提示词变短和端点接受回放字段都不足以证明任务收益，需要可复现的成对测量。
  复用生产回放与既有行为评测，并把失败、截断及缺失用量保留在实验报告中。
  真实模型探测由显式入口运行，离线检查不读取凭据或发送请求。
- release：launchd plist 用例的期望路径经 Path 转串，Windows 不再因反斜杠失败（2e6e973）
- tools：内置契约测试不依赖测试机上的模型 key（fc35783）
  构造 Agent 只为把内置工具登记进 Toolbox，却走了真实的端点发现：本机有
  key 通过，CI 六个 job 全因 MissingConfig 报错。改用桩 registry。
- tools：编码相关用例不再假定本地代码页（f0d81f2）
  编辑链路按 UTF-8 → 本地代码页 → GBK 解码，英文 Windows 的 cp1252 几乎
  什么字节都认：GBK 原文被当 cp1252 乱码读出、0xff 解成 ÿ 不算有损，两个
  用例只在 CI 的 Windows job 上红。改成按本机排在 UTF-8 之后的那个编码造
  原文，有损用例改用三种编码都解不开的 0x81。本机用 cp1252 模拟过。
