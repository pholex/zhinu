# 安全模型

分三层：**默认档靠逐条人工确认，auto / `--yolo` 档靠内核级沙箱，`deny` 规则与不可逆命令拦截在所有档都生效。** 下面写清每层挡什么、不挡什么——已知的洞是明确接受的取舍，不是没想到。

## 确认与权限规则

`bash` 会在你机器上执行模型给出的任意命令，`write_file` / `str_replace` 会改你的文件。默认每条都要你确认（附模型自述的用途和 diff 预览）。

- `/allow` / `/deny` 配权限规则：命中 allow 免确认，命中 deny 强制拦截。
- **`deny` 与危险命令硬拦截（`rm -rf /`、fork bomb 一类）是 bypass-immune 的**：`--yolo` 也拦得住。审批是"用户想不想"，这一层是"绝不"。
- `exit_plan_mode` 的审批同样 bypass-immune：`--yolo` 也要问。否则模型能自行退出 plan 档，"批准后才执行"就是空话。

## 模式与沙箱

| 档 | 会不会问你 |
|---|---|
| **默认** | 写文件、执行命令逐条确认 |
| **auto** | 工作区内改文件、沙箱内跑命令自动放行；危险命令、提权（sudo/doas/su）、写到工作区外、browser / MCP / 插件工具仍要确认 |
| **plan** | 只读规划态：白名单之外的工具一律拦，模型交计划后要你批准才执行 |
| **`--yolo`** | 全放行 |

auto 档**放行的依据是沙箱，不是信任**。所以沙箱不可用时（Windows、没装 bubblewrap、`--no-sandbox`）它自动降级成"只有工作区内改文件免确认"，并且**明说**——静默降级是最坏的失败方式。

沙箱本体（macOS Seatbelt / Linux bubblewrap，默认开启）只允许写工作区、临时目录和构建缓存：家目录文件删不掉、`~/.zshrc` 覆写不了。

## `--yolo`：自动化给满

商业化产品把"每步都要你确认"当成必选项。小羽把它当成一档：无人值守、CI、容器里，确认框只会把任务卡死，所以 `--yolo` 做满——不问、不停、不降速。四条底线仍然生效：

- bash 照常跑在内核级沙箱里（`--yolo` 只关审批，不关沙箱）；
- `deny` 规则一条都不放行；
- `rm -rf /`、fork bomb 一类不可逆命令任何模式下都不执行；
- `exit_plan_mode` 仍要你批准，跨会话消息默认不收。

两点差别值得知道：**`--yolo` 不像 auto 那样把"沙箱可用"当放行前提**——在没有沙箱的平台上（Windows、没装 bubblewrap、`--no-sandbox`），它是真的全放行，bash 能写你有权限的任何地方；另外它刻意不在 Shift-Tab 循环里，得显式敲命令行参数进去。

风险面因此可以一句话讲清：**沙箱内能做的一切，加上联网**。介意联网就 `--no-network`。

## ⚠️ 沙箱不解决凭据外泄

这是明确接受的取舍：**沙箱默认全盘可读、允许联网**，所以免确认的档（auto / `--yolo`）下模型可以不问你就读 `~/.ssh`、`~/.aws` 并 `curl` 出去（默认档里这条命令会弹确认框，你有机会看见）。

沙箱挡的是"写坏你的磁盘"，不是"把你的密钥传出去"。介意的话：

```bash
xiaoyu --no-network          # 或 XIAOYU_SANDBOX_NETWORK=0，断掉沙箱内的网络
```

或者干脆待在默认档。

## 工具边界

`read_file` / `str_replace` / `write_file` 有工作区边界检查；**`bash` 的真隔离只有内核级沙箱那一层**。在沙箱不可用的平台上（Windows、没装 bubblewrap、`--no-sandbox`），bash 仍能写你有权限的任何地方。

零散的环境变量兜底（如无人值守跑 eval 时注入 `PIP_REQUIRE_VIRTUALENV=true` 防止污染系统 Python）只堵具体出口，不等于沙箱。

## 跨会话消息是输入通道，不是提权通道

本机同一用户的任意进程都能给你的会话投消息（隔离靠文件权限，`peers` 目录 0700）。因此：

- 消息带**来源标注**进上下文，不会被当成你的原话。
- 收件会话的确认与 `deny` 规则一条不变——**别人在那边被拦下的动作，不能拿到你这边来做**。
- `--yolo` 会话**默认不收信**（无人值守 + 可被投喂指令，两者叠加才是真风险），要开得显式 `XIAOYU_ENABLE_PEERS=1`。

## folder trust：仓库级可执行配置要先过门

`.mcp.json`（启动即拉起进程）、`.xiaoyu/permissions.txt`（allow 规则免确认）、
工作区 `.env`（能改写端点与开关）都是 **clone 即生效**的配置。陌生目录第一次
要启用它们时会问一次（y/N），答案按 git 根记进用户级信任表
`trusted_folders.json`，之后不再问：

- **headless（`-p` / `--wire` / 管道）不问，直接不信任**：这三类配置整体不生效，
  stderr 有告警；要启用加 `--trust`（记入信任表，一次即可）。
- 信任按 **git 仓库为单位**级联到子目录；家目录 / 文件系统根这类过宽的键
  不可记录（信任表读写两侧都拒绝），这种目录下直接放行——门管的是"陌生仓库"，
  不是你自己的家目录。
- 工作区 `.env` **关不掉这道门**：开关 `XIAOYU_FOLDER_TRUST` 只认真实环境
  变量与用户级 `.env`——被门管的对象不能给自己开门。
- 没有这三类配置的目录完全无感，不问也不记。

## MCP server

第三方 server 是外部代码 + 外部工具描述，安全内建有四条：

- 子进程**环境白名单**——你的 API key 不会漏给 server 进程。
- npx / uvx 包启动前查 **OSV 恶意包库**。
- 内联攻击脚本形状的配置**拒绝启动**。
- 工具描述 / schema 变更**自动隔离**（防 rug-pull），`/mcp approve` 才恢复。

浏览器工具的每个动作都过人工确认——它能以你的身份点任何按钮，**审批就是它的沙箱**。
